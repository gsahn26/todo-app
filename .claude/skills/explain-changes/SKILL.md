# 변경사항 쉽게 설명하기

코드를 바꾼 뒤, 무엇이 왜 바뀌었는지를 긴 이론 없이 짧고 쉬운 말로 설명한다.
듣는 사람은 PHP·MySQL 개발 경험은 있지만 Next.js·React 용어와 긴 이론 설명은 어려워한다고 가정한다.

## 절차

1. 프로젝트 루트에서 바뀐 내용을 확인한다.
   - `git status` 로 바뀐 파일과 새로 생긴 파일을 본다.
   - `git diff` 로 아직 스테이징하지 않은 변경을 본다.
   - 스테이징된 변경이 있으면 `git diff --staged` 도 본다.
   - 새로 생긴 파일(untracked)은 diff에 안 나오므로 파일을 직접 열어 본다.
2. 바뀐 것을 파일 단위가 아니라 "기능 단위"로 묶는다. (예: "할 일 삭제 기능", "완료 표시")
3. 아래 출력 형식대로 설명한다.

## 출력 형식

### 한 줄 요약
무엇이 달라졌는지 한 문장으로. (예: "할 일을 체크하면 줄이 그어지게 바뀌었어요.")

### 화면에서 달라지는 점
사용자가 브라우저에서 직접 보게 되는 변화를 먼저 쓴다. 화면 변화가 없으면 "화면은 그대로예요"라고 쓴다.

### 바뀐 파일
파일마다 2~3줄 이내로 "무엇을" 바꿨고 "왜" 바꿨는지 쓴다.
폴더 역할을 함께 짚어 준다: `app/`은 화면(페이지), `components/`는 화면 조각, `lib/`는 Supabase 연결 같은 공통 코드.
코드는 꼭 필요한 줄만 짧게 보여 준다.

### 처음 보는 용어
설명에 나온 Next.js·React 용어(컴포넌트, useState, props, "use client", 서버 컴포넌트 등)를 한 줄씩 풀어 준다.
가능하면 PHP에 빗대거나 일상 비유를 하나 붙인다. (예: "useState는 화면이 기억하는 메모장")
이미 앞에서 설명한 용어는 다시 쓰지 않는다.

### 직접 확인하는 방법
`npm run dev` 로 실행한 뒤 http://localhost:3000 에서 어디를 눌러서 무엇을 보면 되는지 순서대로 쓴다.

### 주의할 점 (있을 때만)
깨질 수 있는 부분, 아직 안 된 부분, 다음에 할 일을 짧게 쓴다.
Supabase 테이블·권한(RLS)·환경 변수를 건드린 변경이면 반드시 여기서 따로 알린다.

## 지킬 것

- 전체 설명은 화면 한 번에 읽을 수 있을 만큼 짧게 쓴다.
- 이론 설명을 길게 늘어놓지 않는다. "왜"는 한두 문장이면 충분하다.
- 바뀌지 않은 부분은 설명하지 않는다.
- diff에 없는 내용을 추측해서 쓰지 않는다. 확실하지 않으면 "확인이 필요해요"라고 쓴다.
- 설명만 한다. 사용자가 요청하지 않으면 코드를 다시 고치지 않는다.
